## 一、本项目:分布式全局限流的一致性

**问题**:原来的限流是**每实例内存令牌桶**,多副本下每个副本各有一套桶 → 同一 IP 有效阈值 ≈ ×N,不是真全局。

**方案**:把计数放 **Redis**,所有副本读写**同一个 key**;用一段 **Lua 脚本**(`INCR` + 首次 `PEXPIRE` + 比较)做**原子**判定。

**一致性怎么保证**:
- **单一数据源**:全局计数只存在 Redis 一处,所有副本看到的是同一个数 → 计数强一致。
- **原子性**:`INCR+过期+比较` 打包成一条 Lua 脚本,Redis 单线程执行 → 多副本并发下也不会出现"读-改-写"竞态。

**怎么测**(`tests/testcases/test_distributed.py`):
| 测试点 | 断言 |
|---|---|
| 全局阈值约束 | 单 IP 跨两副本猛打 → 放行数 ≈ 全局阈值,而不是 ~2× |
| 跨副本共享 | 副本 A 上耗尽配额 → 副本 B 立刻也 429(证明计数共享) |
| (可扩展)故障降级 | 停掉 Redis → 请求仍放行(fail-open)|
| (可扩展)窗口重置 | 过一个窗口 → 配额恢复 |

**权衡(面试要会说)**:
- Redis 成了**新的依赖和单点** → 需要高可用(哨兵/集群)+ 降级策略。本项目选 **fail-open**(Redis 挂了不阻断流量,可用性优先);也可选 fail-closed(严格限流优先)。这是个**可测的策略点**。
- **固定窗口**实现简单,但有"窗口边界突刺"问题(窗口交界处可能放行 2 倍);更平滑的是**滑动窗口**或 **Redis 令牌桶(Lua)**,代价是复杂度更高。

## 二、分布式系统怎么测(通用面试框架)

被问"怎么测一个分布式系统",按这几个维度答,有条理不漏:

1. **一致性**:多节点读到的数据/状态是否一致;强一致 or 最终一致(最终一致要测**收敛时间**、能否读到旧值)。
2. **可用性 / 故障转移**:杀掉一个节点,流量是否重路由、服务是否可用、在途请求是否不丢。
3. **分区容忍 / 脑裂**:网络分区时行为是否符合预期(CP 拒绝写 / AP 继续但可能不一致);分区恢复后能否**收敛**、有没有脑裂(两个主)。
4. **数据正确性**:并发下的正确性、**幂等**(重复请求结果一致)、消息**顺序/去重**、分布式**事务**是否最终一致。
5. **性能与扩展**:横向扩展是否线性、跨节点延迟、**热点**(某个 key/分片被打爆)。
6. **故障注入 / 混沌工程**:主动注入网络延迟/丢包/分区、节点宕机、**时钟漂移**,看系统是否稳。

**工具**:`k8s`(多副本/杀 pod)、`chaos-mesh`/`toxiproxy`(网络/节点故障)、`Jepsen`(分布式一致性验证的业界标准)、`k6`(跨节点压测)。

## 三、CAP 与一致性模型(概念,常考)

- **CAP**:一致性 C、可用性 A、分区容忍 P。网络分区(P)一定会发生,所以真正是**分区时在 C 和 A 之间取舍**——CP(宁可拒绝也要一致,如 ZooKeeper/etcd)或 AP(宁可返回旧数据也要可用,如 Cassandra/Eureka)。
- **一致性模型**(由强到弱):强一致 → 线性一致 → 因果一致 → **读己之写** → 最终一致。
- **本项目定位**:Redis 全局限流的计数是**强一致**(单点);但 Redis 挂了我们选 fail-open,那一刻是**偏 A**的取舍——面试可以拿这个讲"我在项目里做过的一致性/可用性权衡"。

## 四、分布式数据库怎么测

| 维度 | 测什么 |
|---|---|
| **主从复制** | 主写从读时的**复制延迟**;读写分离下会不会**读到旧数据**(读己之写) |
| **故障切换(failover)** | 主库宕机 → 从库提升为主,**数据不丢、切换时间可接受**、客户端能重连 |
| **分片(sharding)** | 请求是否路由到正确分片;**跨分片查询/聚合/事务**是否正确;分片键选择是否导致热点 |
| **分布式事务** | 2PC / TCC / Saga 的**最终一致**;中途失败能否回滚/补偿;幂等 |
| **一致性校验** | **对账**(核对多副本/上下游数据一致)、`Jepsen` 做一致性/线性化验证 |
| **扩缩容 / 再平衡** | 加减节点时数据**再平衡**是否正确、期间读写是否可用、有无数据丢失 |
| **备份恢复** | 备份可用、能按时间点恢复(PITR) |

一句话:分布式 DB 的测试重心是**数据一致性 + 故障切换 + 分片正确性**,而不只是"增删改查对不对"。

## 五、面试高频分布式 Q&A

**Q:分布式限流怎么做?★**
把计数集中到 Redis(或专门的限流服务):固定窗口(`INCR`+过期)、滑动窗口(有序集合/多窗口加权)、或令牌桶(Lua 原子)。关键是**用一个共享存储 + 原子操作**保证多实例看到同一份配额。本项目用的是 Redis + Lua 固定窗口。

**Q:怎么保证分布式限流又一致又快?**
一致靠单一数据源 + 原子脚本;快靠 Redis 内存操作 + Lua 一次往返。热点 key 可加本地预扣/分桶。Redis 挂了要有降级(fail-open/closed)。

**Q:CAP 讲一下?/ 分区时怎么选?**
见上。要点:P 必然发生,分区时 C/A 二选一,按业务选(支付偏 C,信息流偏 A)。

**Q:脑裂是什么?怎么处理?**
网络分区导致出现两个"主",各自接受写 → 数据冲突。处理:多数派选主(quorum/Raft/Paxos)、fencing token、分区少数派拒绝写。

**Q:幂等怎么设计和测?**
设计:唯一请求 ID + 去重表 / 乐观锁 / 状态机。测:同一请求重复发多次,结果和一次一致、不产生重复副作用(重复下单/扣款)。

**Q:最终一致性怎么测?**
写入后轮询各副本,断言**在容忍时间内收敛**到一致;并显式测"收敛前能读到旧值"这一窗口。

**Q:怎么测一个分布式系统的高可用?**
故障注入(杀节点、网络分区、慢磁盘)+ 持续打流量,断言:错误率在阈值内、故障转移时间达标、在途请求不丢、恢复后自动收敛。用 chaos-mesh / Jepsen。

**Q:你项目里做过哪些分布式相关的?★**(把话题带到本项目)
"我给网关做了 Redis 全局限流,解决每实例限流不全局的问题;写了两条一致性测试证明**跨副本共享配额**;并做了 fail-open 的降级取舍。这让我对**分布式一致性/可用性的权衡**有了动手经验。"
