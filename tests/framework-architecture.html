四条能讲深的主线

每条都对应上面某一层 / 某几个模块
主线一

接口自动化 + CI 门禁

  • 分层框架:用例 / 数据 / 断言 / 报告解耦
  • 数据驱动:负向用例写在 yaml,加一行=加一个攻击面
  • 一键起栈 + 两阶段执行,Allure 报告,做成 PR 门禁
主线二 · 最见深度

故障注入

  • 熔断状态机:连续 5xx 打开 → 冷却 → 半开探测 → 恢复,全流程断言
  • 判定技巧:用响应头有无 X-Served-By 区分"网关短路"与"后端错误"
  • 延迟注入,并记录"上游无独立超时"这一风险
主线三

性能 / 限流压测

  • k6 以 4× 阈值加压,断言放行流量 p95 与 429 比例
  • 退出码可接 CI,当性能门禁
  • 对比单 IP / 多 IP 两种画像,佐证限流键设计
主线四

契约 + 监控断言

  • 契约测试:拿 OpenAPI schema 校验响应,面向契约而非实现
  • 监控断言:发请求前后读 /metrics,断言计数器确实 +1
  • 校验指标 label 用路由前缀(高基数防护)

设计亮点:并行 / 串行隔离策略(避免 flaky)

按客户端隔离 可并行

鉴权 / 路由 / 负载均衡 / 限流 / 契约 / 监控。每个 client 用独立源 IP(X-Forwarded-For),限流桶天然隔离 → -n auto 并行提速。

服务端共享状态 须串行

熔断器是按路由的全局状态,打开会波及所有同路由请求 → 独占路由、串行执行、用例前后复位到 closed。

面试一口气叙述模板

S/T › 一个承担鉴权、限流、负载均衡、熔断的 Go API 网关,改配置全靠手工验证,缺自动化回归。我从 0 搭接口自动化框架并接入 CI 做 PR 门禁。
A › 分层设计把样板下沉;数据驱动写负向与安全用例;用可控测试桩做故障注入,稳定复现熔断状态机与超时;引入 OpenAPI 契约校验和 Prometheus 监控断言;用 docker-compose 一键起栈 + GitHub Actions 两阶段执行 + Allure 报告。
R › 40+ 用例覆盖 6 大模块,回归从手工数十分钟降到自动数十秒,做成 PR 门禁;额外产出 4 条有依据的风险评估(上游无超时 / TrustedProxies / metrics 无鉴权 / LB 无健康检查)。
