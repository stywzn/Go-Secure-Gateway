# 测试点总结(分模块)

针对 Go-Secure-Gateway 网关接口的自动化测试点清单,按模块拆分。每条给出
**测试点 / 预期结果 / 优先级**。优先级:P0=核心必测,P1=重要,P2=补充。

> 触发手段说明:被测后端是**可控测试桩**,可用 `?status=<码>` 强制状态码、
> `?delay=<时长>` 注入延迟、`POST /storage/_reset` 重置状态。异常路径基本都能
> 靠它稳定构造。

---

## 1. 鉴权模块(JWT Auth)

**功能**:所有受保护路由必须携带合法的 `Authorization: Bearer <JWT>`,否则拒绝。

| # | 测试点 | 预期结果 | 优先级 |
|---|---|---|---|
| 1.1 | 携带合法 token 访问 `/interaction/ping` | 200,请求透传到后端 | P0 |
| 1.2 | 不带 `Authorization` 头 | 401,提示缺少请求头 | P0 |
| 1.3 | 头格式错误(如 `Basic xxx`、无 `Bearer` 前缀) | 401,提示格式错误 | P0 |
| 1.4 | token 过期(exp 已过) | 401 | P0 |
| 1.5 | token 无 exp 声明 | 401(强制要求 exp) | P1 |
| 1.6 | 签名密钥错误(用别的 secret 签) | 401 | P0 |
| 1.7 | 算法混淆攻击:用 `alg=none` 或 `RS256` 伪造 | 401(只接受 HS256) | P0 🔒 |
| 1.8 | token 被篡改(改 payload 不改签名) | 401 | P1 |
| 1.9 | `Bearer` 后为空 / 多余空格 | 401 | P2 |
| 1.10 | 合法 token 但 `user_id` 为字符串 / 数字 | 200,且下游 `X-User-Id` 正确 | P1 |

**已知风险点**:算法混淆(1.7)是 JWT 最经典漏洞,重点测。

## 2. 限流模块(Rate Limiting,按 IP)

**功能**:每个客户端 IP 令牌桶限流,超出返回 429。

| # | 测试点 | 预期结果 | 优先级 |
|---|---|---|---|
| 2.1 | 突发在 burst 容量内的请求 | 全部 200 | P0 |
| 2.2 | 瞬间超过 burst 的请求 | 超出部分 429 | P0 |
| 2.3 | 达到限流后等待令牌恢复再请求 | 恢复后重新 200 | P1 |
| 2.4 | 不同 IP(不同 `X-Forwarded-For` / RemoteAddr)互不影响 | 各自独立计数 | P1 |
| 2.5 | 429 响应体/状态码符合约定 | body 含错误信息,状态 429 | P2 |
| 2.6 | 限流是否发生在鉴权之前 | 未带 token 且超限时,先返回 429 还是 401(验证中间件顺序) | P1 |
| 2.7 | 长时间大量不同 IP 后内存是否回收 | 空闲 IP 被 TTL 清理,不泄漏 | P2 |

**已知风险点**:
- `c.ClientIP()` 取值依赖 Gin 的 `TrustedProxies` 配置。若部署在多层代理后,
  可能所有请求被识别成同一个 IP(网关自己),导致**全局被限流**或**伪造 XFF 绕过限流**。→ 2.4 重点测。
- 并行跑测试时,限流会让无关用例莫名 429 → 测试环境应调高阈值或隔离限流用例。

## 3. 路由与反向代理模块

**功能**:按 `path_prefix` 把请求转发到对应后端;可配置剥离前缀;透传身份/转发头。

| # | 测试点 | 预期结果 | 优先级 |
|---|---|---|---|
| 3.1 | `/interaction/ping`(strip=false) | 后端收到的 path 保留前缀 `/interaction/ping` | P0 |
| 3.2 | `/storage/files/1`(strip=true) | 后端收到 `/files/1`(前缀被剥离) | P0 |
| 3.3 | 精确命中前缀本身 `/compute` | 正常转发 | P1 |
| 3.4 | 带查询参数 `/compute/run?n=42` | 查询参数完整透传 | P1 |
| 3.5 | 各种 HTTP 方法(GET/POST/PUT/DELETE) | 方法与 body 完整透传 | P0 |
| 3.6 | 未配置的前缀 `/unknown/x` | 404 | P1 |
| 3.7 | 鉴权后 `X-User-Id` 注入下游 | 后端 echo 出正确 user_id | P0 |
| 3.8 | 客户端伪造 `X-User-Id` 头 | 被网关删除后重设,不能伪造 | P0 🔒 |
| 3.9 | `X-Forwarded-Proto` / `X-Forwarded-Host` 被正确设置 | 后端收到转发头 | P2 |
| 3.10 | 大 body / 特殊字符路径 / URL 编码 | 正确转发不损坏 | P2 |
| 3.11 | 后端返回流式响应(如 SSE) | 能正常流式透传(不被缓冲坏) | P2 |

**已知风险点**:
- 身份伪造(3.8)是安全测试重点。
- 网关对**上游调用没有独立超时**:后端 `?delay=30s` 会一直等到网关的
  `WriteTimeout`(15s)才断开。→ 见 5.x / 超时相关,值得作为"发现的问题"记录。

## 4. 负载均衡模块(轮询 RoundRobin)

**功能**:一个路由配多个后端时,请求轮流分发。

| # | 测试点 | 预期结果 | 优先级 |
|---|---|---|---|
| 4.1 | `/storage` 连发 N 次(N=副本数的倍数) | 响应头 `X-Served-By` 在 `storage-a`/`storage-b` 间均匀轮转 | P0 |
| 4.2 | 请求数不是副本数整数倍 | 分布尽量均匀,无遗漏/无偏斜到一台 | P1 |
| 4.3 | 高并发下轮询是否线程安全 | 无 panic、无数据竞争(`go test -race`) | P1 |
| 4.4 | 单后端路由 | 始终命中同一后端 | P2 |
| 4.5 | 其中一个后端不可用 | 结合熔断/错误处理观察行为(是否仍轮询到坏节点) | P1 |

**已知风险点**:当前轮询**不做健康感知**——坏节点仍会被轮到(4.5),这是可讨论的
设计取舍/待改进点。

## 5. 熔断模块(Circuit Breaker,按路由)

**功能**:连续失败(5xx)达阈值后熔断打开,拒绝请求;冷却后半开放行一个探测。

| # | 测试点 | 预期结果 | 优先级 |
|---|---|---|---|
| 5.1 | 用 `?status=500` 连续打到阈值(默认 5 次) | 达阈值后熔断打开 | P0 |
| 5.2 | 熔断打开后继续请求 | 直接 503(Circuit Open),不再打后端 | P0 |
| 5.3 | 打开后等待冷却时间(默认 10s) | 进入半开,放行**一个**探测请求 | P0 |
| 5.4 | 半开时并发多个请求 | 只有一个探测通过,其余被拒 | P1 |
| 5.5 | 半开探测成功(后端恢复正常) | 熔断关闭,恢复正常流量 | P0 |
| 5.6 | 半开探测失败(`?status=500`) | 立即重新打开 | P1 |
| 5.7 | 4xx 是否计入失败 | 不计入(只有 5xx 触发熔断) | P1 |
| 5.8 | 后端连接错误(非 5xx,直接连不上) | ErrorHandler 返回 502,并计为失败 | P1 |

**说明**:这一模块几乎全靠可控 mock 才能稳定测——这是"可控测试桩"价值的最佳例证,
面试可重点讲。

## 6. 运维 / 探针 / 可观测模块

**功能**:健康探针、就绪探针、指标暴露。

| # | 测试点 | 预期结果 | 优先级 |
|---|---|---|---|
| 6.1 | `GET /healthz`(无需鉴权) | 200 | P0 |
| 6.2 | `GET /readyz` 正常运行时 | 200 | P0 |
| 6.3 | 优雅关闭期间 `GET /readyz` | 503(触发 K8s 摘流量) | P1 |
| 6.4 | `GET /metrics` | 200,含 `gateway_http_requests_total` 等指标 | P1 |

| 6.7 | `/debug/token` 在 `debug=false` 时 | 404(后门不暴露) | P0 🔒 |
| 6.8 | `/debug/token` 在 `debug=true` 时 | 200,返回可用 token | P1 |

**已知风险点**:`/metrics` 公开无鉴权(6.4),可作为"是否应加保护"的讨论点。

## 测试类型分布(面试可用的一句话)

- **功能/正向**:1.1、3.1~3.5、4.1、6.1~6.4 —— 验证"该通的通"
- **异常/负向**:1.2~1.9、2.2、5.1~5.8 —— 验证"该拦的拦"
- **边界**:2.1/2.3、4.2、7.1/7.2 —— 临界值行为
- **安全**:标 🔒 的几条 —— 最能体现深度
- **并发/稳定性**:2.7、4.3、5.4 —— `-race`、压测

## 重点值得当"发现的问题"记录的候选

1. 上游调用无独立超时,慢后端会拖到 WriteTimeout(3.x / 8.4)。
2. `ClientIP` / TrustedProxies 未显式配置,多层代理下限流可能失效或误伤(2.x / 8.6)。
3. `/metrics` 公开无鉴权(6.4)。
4. 负载均衡无健康检查,坏节点仍被轮询(4.5)。

> 这些不一定是"bug",但都是**有依据的风险点**——面试时说"我测出/评估了这些风险并给出建议"比只说"功能都正常"有分量得多。

## 9. 有状态流程(E2E CRUD 时序)

**功能**:通过 `/data` 路由(单后端,内存存储)做完整增删改查。对应实现:
[cmd/mockbackend/main.go](../cmd/mockbackend/main.go) 的 CRUD + [proxy.go](../internal/proxy/proxy.go) 的前缀剥离。

| # | 测试点 | 预期结果 | 优先级 |
|---|---|---|---|
| 9.1 | 创建 → 用返回 id 查询 | 201 后可 200 查到,字段一致 | P0 |
| 9.2 | 列表 count 随创建增长 | count 正确 | P1 |
| 9.3 | 更新已存在项 | 200,内容被替换 | P1 |
| 9.4 | 删除后再查 | 首次 204,再查 404 | P0 |
| 9.5 | 删除不存在项 | 404 | P1 |
| 9.6 | PUT 幂等性(同一请求发两次) | 结果一致 | P2 |
| 9.7 | 创建时传非法 JSON | 400 | P1 |
| 9.8 | `/data/_reset` 后列表为空 | count=0(测试隔离) | P0 |

> ⚠️ 教学点:CRUD 特意放在**单后端** `/data`,不用 2 副本的 `/storage`——因为轮询 LB
> 会把请求打到状态**互相独立**的两个副本上,导致"创建在 A、查询到 B → 404"。这正说明:
> **有状态服务放在 LB 后必须靠共享存储(Redis/DB)或会话保持**,是很好的面试话题。

## 11. 分布式 / 多副本(重点讨论,🔴 功能限制)

**功能现状**:限流器与熔断器都是**每实例内存态**([ratelimit.go](../internal/middleware/ratelimit.go)、
[breaker.go](../internal/proxy/breaker.go)),**不跨副本共享**。

| # | 测试点 | 预期结果 | 优先级 |
|---|---|---|---|
| 11.1 | 起 2 个网关副本,总限流阈值 | 实际有效阈值 ≈ 单实例的 2 倍(非全局) | 讨论 |
| 11.2 | 熔断状态是否跨副本共享 | 不共享,各自独立 | 讨论 |

> 这是**项目当前的架构限制**,不是 bug。面试口述:"限流是每实例的,多副本下不是全局;
> 要全局需引入 Redis 做共享计数(`INCR`+过期 或 令牌桶 Lua)"。**知道并能讲 = 满分**,不必真实现。

## 附录 B:测试没覆盖(🟢) vs 项目没功能(🔴)

回答"是测试点没覆盖全面,还是项目本身没有那些功能"——两者都有,分类如下:

**🟢 功能已有,只是还没写测试(可直接补测试):**
§9 有状态 CRUD、§10 性能压测、§12.1/12.2/12.4~12.7 协议与关闭、错误一致性。

**🔴 项目本身没有此功能(写测试只能确认限制,更适合作为改进建议):**
- 全局限流/熔断(多副本共享)——需 Redis(§11)
- 上游调用级超时(§12.3)
- TLS / HTTPS(§12.8)
- CORS(§12.9)

> 面试话术:"功能类的我做了完整回归;对项目**缺失的能力**(全局限流、上游超时、TLS、CORS),
> 我在测试中识别为风险并给出改进建议。" —— 这体现的是**测试设计 + 架构判断**,不是单纯点点点。
