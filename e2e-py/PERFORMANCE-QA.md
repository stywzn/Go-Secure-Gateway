# 性能测试:我做了什么 / 全套有哪些 / 为什么这么取舍(面试应对)

> 面试主打的是这个 pytest 框架;性能是其中一环。被问"性能你做了哪些、为什么没做全套"时,照这份讲——**重点不是"全做了",而是"按目标做了对的部分,且清楚完整体系"**。

---

## 一、我在这个框架里实际做了什么 ✅

**k6 限流压测 + CI 性能门禁**(脚本:`perf/ratelimit.js`,门禁:`.github/workflows/e2e-py.yml`)。

- **目标**:不是测"能扛多少 QPS",而是**验证限流功能在压力下真的生效 + 防止性能退化**(性能左移进 CI)。
- **怎么做**:20 VU × 10s 并发压 `/interaction/ping`,`setup()` 先拿一次 token 复用。
- **关键设计——用 thresholds 当门禁**(不达标 → k6 退出码非 0 → 流水线变红):
  | threshold | 含义 | 为什么 |
  |---|---|---|
  | `rate_limited_429 count>0` | **必须真触发了限流** | 防"限流形同虚设"却测试通过 |
  | `http_req_duration p(95)<800ms` | 压力下延迟不崩 | 性能基线 |
  | `checks rate>0.99` | 99%+ 无 5xx | 压力下不出服务错误 |
- **效果**:每次改动跑 CI 就自动验证"限流生效 + 延迟达标 + 不报错",**改坏了立刻拦住**。

> 一句话:我做的是**功能性能门禁**——把"限流对不对 + 性能有没有退化"变成 CI 里自动、可复现的关卡。

## 二、完整性能测试体系(全套长什么样)

面试要显得懂全貌。性能测试(非功能)按施压方式分这几种:

| 类型 | 回答的问题 | 怎么压 | 什么时候做 |
|---|---|---|---|
| **负载测试 Load** | 预期峰值下**达标吗** | 加到预期 QPS 并保持,对照 SLO | 有明确性能指标要求时 |
| **压力测试 Stress** | **上限在哪**、崩溃/恢复行为 | 不断加压直到拐点 | 想知道容量天花板 |
| **稳定性 Soak/浸泡** | 有没有**内存/连接泄漏**、衰减 | 中等压力跑几小时~一夜 | 大版本上线前 |
| **尖峰 Spike** | 瞬间暴增扛不扛、限流生效吗 | 流量 0→峰值瞬间拉起 | 秒杀/突发场景 |
| **容量/可扩展** | 加机器吞吐涨不涨 | 逐步扩副本看吞吐 | 容量规划 |

> 辨析(高频):**负载=达标吗(有目标值);压力=上限在哪(压过极限);稳定性=有没有泄漏(靠长时间);尖峰=突刺扛不扛。**

## 三、我做了哪些、没做哪些、为什么(核心取舍)⭐

| 类型 | 我做了吗 | 原因 |
|---|---|---|
| **功能性能门禁**(限流+延迟) | ✅ 做了(CI) | 对**接口/框架测试岗**,这最有价值:自动、防退化、验证功能正确 |
| **压力测试(找拐点)** | ✅ 做了(容量基准,gateway 项目侧) | 单独压到 ~12k QPS 找饱和拐点 + pprof 定位瓶颈 |
| **负载测试 Load** | ❌ 没铺开 | **自建项目没有业务 SLO**,没有"达标线"当对照,做纯负载测试不知道拿什么参照;直接压力测试找上限信息量更大 |
| **稳定性 Soak** | 🟡 没做 | 要跑几小时,且**单机 Docker 环境长时间跑收益低**(资源受宿主干扰,非真实生产);标为"可补" |
| **尖峰 Spike** | 🟡 部分 | 限流压测已覆盖"高并发下限流生效",完整 spike 曲线未单独做 |

> **答题核心**:"我按**项目目标和成本**做取舍——对接口/框架测试岗,**性能门禁(功能正确+防退化)** 价值最高,所以优先做且做进 CI;负载测试缺 SLO 基准、soak 单机收益低,所以没铺开。**但我清楚每种测什么、什么时候该做。**"

## 四、这些没做的,该"什么时候 + 怎么做"

面试官追问"那要做你会怎么做",答得出方案 = 懂:

- **负载测试**:先和产品/架构定 **SLO**(如 P95<200ms @ 5000 QPS),k6 用 `constant-arrival-rate` 固定打 5000 QPS 30 分钟,看是否达标。
- **压力/阶梯**:k6 `ramping-vus` 阶梯加压(50→100→200→300),画 QPS-延迟曲线找拐点(我已用两档并发对比近似做到,定位 ~12k 饱和)。
- **稳定性 Soak**:中等压力(如 50 VU)跑 4~8 小时,**盯内存/连接数/Goroutine 是否缓涨**(泄漏),配 Prometheus/Grafana 看曲线。
- **尖峰 Spike**:`ramping-vus` 用极短时间(几秒)从 0 拉到极高,看限流是否顶住、恢复是否正常。
- **共性**:压测时**盯监控大盘**(不只看 k6 报告),用 pprof 定位瓶颈,是 CPU/内存/GC/锁哪一环。

## 五、达到了什么目标 / 效果(讲价值)

- **功能正确**:自动验证"限流真的拦得住"(429 必现),不靠人肉点。
- **防退化**:性能基线(p95<800ms、无 5xx)进 CI,**任何改动破坏性能立即被拦**。
- **可复现**:脚本化 + CI,谁跑都一样,不是一次性手工压测。
- **懂容量**:额外的容量基准知道系统天花板(~12k QPS),为扩容/SLO 提供依据。

> 价值升华:**我把性能测试从"上线前临时压一次"变成了"CI 里持续、自动、可复现的质量关卡"——这是性能左移。**

## 六、30 秒面试话术(背这段)

> "性能我做了两层:**工程化层**——把 k6 限流压测接进 CI 当性能门禁,不达标(限流没触发/p95 超标/有 5xx)就卡住流水线,这是性能左移和防退化;**探索层**——单独做容量基准压到约 1.1 万 QPS 找到饱和拐点,用 pprof 定位瓶颈。
>
> 负载和稳定性 soak 我没铺开,是主动取舍:自建项目没有业务 SLO,纯负载测试缺达标基准;soak 单机 Docker 收益低。但我清楚完整体系——负载测达标、压力测上限、soak 查泄漏、尖峰测突刺——以及每种什么时候该做、怎么做。"

## 七、可能的追问 & 接法

| 追问 | 怎么接 |
|---|---|
| 为什么用 k6 不用 JMeter? | Go 内核单机压力强、脚本可版本管理、**thresholds 天生适合 CI 门禁**(退出码) |
| thresholds 和 checks 区别? | check 只记录不影响退出码;threshold 不达标 → 退出码非 0 → 能 fail CI |
| 怎么找系统性能上限? | 阶梯加压看 QPS 不涨、延迟陡增的拐点(我定位到 ~12k) |
| soak 能发现什么? | 短测发现不了的**内存/连接泄漏、性能衰减** |
| 性能测试为什么要进 CI? | 防退化——性能不是测一次,是每次改动都不能变差 |
| 压测发现 p99 飙升怎么定位? | 看监控(CPU/内存/GC)→ pprof 抓火焰图找热点函数 |
