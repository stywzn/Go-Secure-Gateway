# 面试问答题库(围绕本项目)

按主题分组。答案是**口语化要点**,不用背原文,理解逻辑后用自己的话讲。带 ★ 的是最可能被追问、最能加分的。

---

## 一、项目理解

**Q:简单介绍一下这个项目。**
从 0 独立搭的一套接口自动化框架,被测是一个 Go 写的 API 网关(鉴权/限流/负载均衡/熔断/超时/可观测)。分层设计,覆盖 9 模块 21 用例,并落地了故障注入、k6 压测、契约测试、CI 门禁。回归从手工数十分钟降到秒级、零 flaky。

**Q:为什么选一个网关当被测系统?**
它把常见后端能力(鉴权/限流/LB/熔断/可观测)浓缩在一个边界清晰的服务里,能覆盖足够多的测试类型;又自带**可控测试桩**(能强制返回任意状态码、注入延迟),异常路径能确定性复现;还不至于庞大到无法完全掌控——适合把每个点都讲透。

**Q:这个项目最大的难点/最有成就感的地方?★**
讲那个"一个逗号引发跨用例串扰"的 debug(见 STAR.md 难点1):症状是路由测试莫名 429,根因是随机 IP 的 f-string 多个逗号生成了非法 IP、网关退回共享限流桶。靠"提假设→做实验证伪→打印真实值"定位。成就感在于:症状离病根十万八千里,还是把它揪出来了,并由此真正理解了"flaky 的根源是共享状态"。

## 二、架构类

**Q:网关是分布式的吗?★**
设计成**无状态**的,支持分布式部署(k8s 里配了 2 副本)。因为鉴权用 JWT、身份在 token 里、服务端不存 session,所以任意副本都能处理任意请求,可水平扩展、随时重启。**但要诚实指出**:限流/熔断是每实例内存态,多副本下不是全局的——有效阈值会翻倍,生产要用 Redis 做全局计数。

**Q:如果是分布式,你怎么做测试?★**
分层:① 无状态验证(杀掉一个副本,流量重路由、在途请求不丢、无 session 丢失);② 每实例状态验证(起 N 副本,证明限流是每实例的、有效阈值≈N×);③ 全局限流验证(若上了 Redis,多副本同时压,断言总放行量受全局阈值约束);④ HA/故障注入(杀节点、网络分区,验证熔断+探针+重试);⑤ 规模化压测(k6 测跨副本聚合吞吐/延迟)。工具:k8s、k6、toxiproxy/chaos-mesh。

**Q:系统是微服务的吗?★**
是**微服务 + API 网关**的经典架构:网关是统一入口,做鉴权/限流/可观测这些横切关注点;后面挂多个独立后端服务,各自独立部署、HTTP 通信。本项目后端是可控测试桩,但架构形态和真实微服务一致,所以测试既覆盖网关本身,也覆盖"网关→后端"的端到端链路(前缀剥离、身份透传、CRUD 时序)。

**Q:网关到底解决什么问题?**
把每个服务都要做的横切关注点(鉴权、限流、日志、监控、TLS)收到入口统一做,后端服务只管业务;还提供统一入口做路由、负载均衡、熔断降级。

**Q:无状态为什么重要?**
无状态 = 不存跨请求/需持久化的业务数据,所以任意副本处理任意请求、可随意扩缩容和重启;代价是像限流这种"计数"要么接受每实例、要么外置到 Redis。

## 三、测试设计与深度

**Q:怎么保证测试不 flaky?★**
① 按 IP 隔离限流桶(每个 client 独立源 IP);② 共享服务端状态的熔断用例串行独占、前后复位;③ 故障场景用可控桩做到确定性,不依赖真实后端的"心情";④ 有状态用例前 reset 清库。

**Q:熔断怎么测的?怎么区分"网关短路"和"后端错误"?★**
连续 `?status=500` 打到阈值使熔断打开,再断言后续请求被网关**短路**:503 且**无 `X-Served-By` 头**——因为熔断时请求根本没到后端,而后端每次响应都会带 `X-Served-By`。所以"503+无 X-Served-By"=网关短路,"503+有 X-Served-By"=后端自己错,一头就分清了。冷却后进半开,放行一个探测成功→关闭。

**Q:契约测试 vs 普通断言 vs 集成测试?**
普通断言把"响应长啥样"写死在用例里,实现一改用例容易一起漂;契约测试以 Schema(OpenAPI/JSON Schema)为唯一真相源校验结构,接口一偏离立刻暴露,维护成本低。集成测试更关注多组件协作是否正确,契约测试专注"接口形状"这一层。

**Q:没有接口文档,你怎么设计用例?**
先探索(照实际请求打一遍、抓包看真实结构),再按测试设计方法覆盖:等价类、边界值、异常/负向、安全(越权/伪造)、幂等与并发。同时推动补文档/契约,后续用契约测试守住。

**Q:有状态接口(CRUD)怎么保证用例隔离?**
每个用例前调 reset 清空后端存储 + 用独立的数据;断言走完整生命周期(建→查→改→删→再查 404),确保不留脏数据、用例间不串扰。

**Q:功能测试和性能测试的边界?★**
功能测试验证"对不对"(限流会不会返回 429),要确定性——我把测试环境阈值调低让它稳定触发;性能测试验证"扛不扛得住"(高并发下 p95、429 比例),交给 k6 单机压到上万 QPS。别用 pytest 顺序请求硬凑压测。

**Q:覆盖率追求 100% 吗?**
不唯覆盖率。覆盖率是参考,更看**风险驱动**:核心链路、异常路径、安全边界优先;有些路径(比如上游无超时)测出来是"确认风险",比堆覆盖率数字更有价值。

## 四、工程 / CI / 工具

**Q:为什么用 pytest?**
生态强、fixture 依赖注入优雅、参数化/标记/插件(xdist 并行、allure 报告)丰富、和 CI 好集成;纯 Python 上手快、能复用被测方的语言生态。

**Q:fixture 是什么?scope 有哪些?**
fixture 是可复用的前置/资源,用例把它当参数"点名",pytest 自动创建并注入(依赖注入)。scope:function(默认,每用例一份)/class/module/package/session,越宽复用越多但越容易共享状态串扰;所以每用例独立的 client 用 function,一次性的探活用 session。

**Q:数据驱动怎么做的?好处?**
把鉴权用例外置到 YAML,`yaml.safe_load` 读出来用 `parametrize` 遍历。好处:加攻击面只改数据、不动代码;用例与数据解耦、可读性高。

**Q:CI 门禁怎么设计的?为什么两阶段?★**
GitHub Actions:push/PR → 起 compose 栈 → 跑 pytest → k6 压测 → 传 Allure,任一失败拦 PR。两阶段是因为熔断用例是破坏性的(打开 /compute 服务端熔断),不能和别的 /compute 用例并行,否则串扰;所以"除熔断外并行 + 熔断单独串行",既提速又不 flaky。

**Q:为什么用 k6 不用 Locust/JMeter?**
k6 是专职压测里认知度高、单机性能强、`thresholds→退出码` 天生适合当 CI 性能门禁,脚本轻。Locust 同为 Python、有网页图表、能复用被测代码,是很好的替代;JMeter 老牌但偏重、GUI 为主。选型看团队栈和场景。

**Q:测试桩(mock)为什么重要?**
真后端启动慢、依赖多、行为不可控(没法让它"刚好返回 503")。可控桩让结果只取决于被测网关,做到确定、可控、可重复——这是自动化测试的命根子。

## 五、发散 / 开放题

**Q:如果重新设计这个框架,会怎么改?★**
① 客户端 DRY(抽一个 `_request` 核心方法);② 加会话级探活夹具,栈没起时快速失败给指引;③ pytest.ini 上 `--strict-markers`+`filterwarnings`,打错标记直接报错、报告更干净;④ 契约测试直接吃 `openapi.yaml` 而非内联 schema;⑤ Allure 报告发布到 GitHub Pages 拿在线链接;⑥ 上 Redis 全局限流并补分布式测试。

**Q:怎么测一个你完全没见过的接口?**
先读文档/契约或抓包摸清入参出参 → 正向跑通 → 等价类/边界/异常/安全设计用例 → 关注幂等、并发、鉴权、错误码是否规范 → 有依赖就 mock、有契约就上契约测试。

**Q:上线前发现一个 flaky 用例,怎么处理?**
不要简单 retry 掩盖。先定位根因:是共享状态?时序/竞态?外部依赖?环境?——本项目里我就是靠"打印真实值+最小复现"把一个 flaky 追到一个 f-string 逗号。根因修掉,而不是加 sleep/retry。

**Q:如何测第三方依赖(支付、短信)?**
用 mock/桩隔离,别打真实第三方(慢、花钱、不可控);对它们的接口做**契约测试**保证双方约定不漂;必要时用录制回放。

**Q:如果限流要做成全局的(Redis),测试要怎么变?★**
新增测试点:多副本/多客户端同时压,断言**总放行量受全局阈值约束**(而不是每实例各放一份);还要测 Redis 挂掉时的降级策略(失败开放还是失败关闭)、以及分布式计数的一致性与延迟。

**Q:怎么把这套框架推广到团队?**
分层让新增用例成本低;文档(README/STAR)+ 清晰的运行命令;接进 CI 做门禁形成习惯;用数据驱动/契约降低维护成本;沉淀公共 client/fixture 供复用。
