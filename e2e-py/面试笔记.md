## 1. Prometheus CounterVec 的惰性输出:为什么"指标会消失"　【实战亮点 + 面试】

**结论先行**:带 label 的 `CounterVec`,在**任何 label 组合被观测到之前,`/metrics` 完全不输出它** ——
连 `# HELP` / `# TYPE` 说明行都没有。这是客户端库的正常语义,不是缺陷。

网关侧的定义(`internal/metrics/metrics.go`):

```go
RequestCount = promauto.NewCounterVec(
    prometheus.CounterOpts{Name: "gateway_http_requests_total", ...},
    []string{"method", "route", "status"},   // ← 三个 label
)
```

有 label 就意味着它不是**一个**数,而是**一张表** —— 每个 `{method,route,status}` 组合一行。
表是空的时候,整张表都不显示。

实测(刚重启的网关):

```
$ curl -s localhost:8080/metrics | grep -c gateway_http_requests_total
0
$ curl -s -H "Authorization: Bearer $TOK" localhost:8080/interaction/ping   # 打一个业务请求
$ curl -s localhost:8080/metrics | grep -c gateway_http_requests_total
3      # HELP + TYPE + 一行数据
```

**由此引出的测试设计原则**:断言"指标存在"是脆的,断言"指标随我的操作增长"才是稳的。
前者依赖环境状态,后者只依赖自己的行为。详见 [`STAR.md`](STAR.md) 核心谈资第 7 条。

**两个配套细节**:

- 解析工具 `framework/prometheus.py` 的 `counter_total()` **找不到指标时返回 `0.0` 而非抛异常**。
  因为"指标不存在"和"值为 0"语义上是一回事 —— 都表示这件事还没发生过。
  返回 0.0 之后调用方能直接写 `after > before`,不必先判断存在性。
- 断言写 `after > before` 而**不是** `after == before + 1`。
  `-n auto` 并行时别的 worker 也在打这个网关,计数器涨的不止 1。
  **共享环境里应当断言变化的方向,而不是精确值。**

**面试延伸**:被问"指标设计要注意什么"可以接 **label 基数(cardinality)**。
网关这里 `route` 用的是**路由前缀**(`/interaction`)而非原始路径(`/interaction/ping`),
就是为了控制基数 —— 每个不同 URL 一条时间序列会撑爆 Prometheus 存储。

## 2. 会话级探活 fixture:把 14095 行报错变成 16 行　【实战 + 面试】

**问题**:忘了 `docker compose up -d` 就跑测试,输出是 **14095 行**、20 个 FAILED + 1 个 ERROR,
全是同一个 `ConnectionError`。真实原因只有一个,却被淹没在一万四千行堆栈里。

**做法**:加一个 `scope="session"` + `autouse=True` 的 fixture,整场开始前 ping 一次 `/healthz`,
不通就 `pytest.exit()` 直接终止,一条用例都不跑。

效果:**14095 行 → 16 行**,退出码 1(CI 可识别)。

写的过程踩了三个坑,每个都值得单独讲。

### 2.1 Python 生成器:为什么 fixture 报 "did not yield a value"

**函数里只要出现 `yield`,它就不再是普通函数,而是生成器** —— 调用它不执行函数体,
而是返回一个生成器对象;函数体在被迭代时才跑,跑到 `yield` 就**暂停**并交出值,
下次迭代**从暂停处继续**。

```python
def gen():
    print("函数体在执行")
    yield 42
    print("yield 之后的代码")

g = gen()        # 什么都不打印 —— 函数体一行没跑
next(g)          # 这时才打印"函数体在执行",拿到 42,停在 yield
next(g)          # 从 yield 处续跑,打印"yield 之后的代码"
```

**pytest 正是靠这个特性实现 fixture 的 setup/teardown**:

```python
@pytest.fixture
def db():
    conn = connect()   # yield 之前 = setup
    yield conn         # 交给用例,函数在此暂停
    conn.close()       # 用例结束后续跑 = teardown
```

**我踩的坑**:探活 fixture 里写了 `return ...` 而后面还有 `yield`。
`return` 在 `yield` 之前结束了生成器 → 一个值都没交出来 → pytest 报
`ValueError: fixture did not yield a value`,21 条用例全 error,比不加 fixture 还糟。

**修法**:探活**没有任何东西要清理**,所以根本不需要 `yield` —— 写成普通函数即可,
也就绕开了这个坑。**判断标准:有 teardown 才用 `yield`,没有就别用。**

### 2.2 `except Exception` 会把 `pytest.exit` 自己吞掉

```python
from _pytest.outcomes import Exit
Exit.__mro__                   # (Exit, Exception, BaseException, object)
issubclass(Exit, Exception)    # True  ← 关键
```

`pytest.exit()` 的实现是**抛一个 `Exit` 异常**,而它继承自 `Exception`。所以:

```python
try:
    resp = requests.get(health_url)
    if resp.status_code != 200:
        pytest.exit("...")      # ← 抛 Exit
except Exception:               # ← 被这里接住了,退出失效
    ...
```

**修法**:把 except 收窄到 `requests.exceptions.RequestException`(requests 所有异常的基类),
让 `Exit` 能正常穿透出去。

**通用原则:`except` 要抓具体类型,别抓 `Exception`。**
抓得太宽会把本该往上抛的**控制流异常**一起吞掉。这是活生生的例子,
比背"不要裸 except"有说服力。

**顺带**:`try` 块要尽可能小 —— 只把真正可能抛网络异常的那一句放进去,
状态码判断挪到 `try` 外面。这样你清楚知道自己在防什么。

### 2.3 报错消息该写什么

好的失败信息回答三件事:**什么坏了、为什么、怎么办**。而且两种失败病因不同,消息也该不同:

| 情况 | 消息要点 |
|---|---|
| 连不上 | 栈没起 → 引导 `docker compose up -d`;并提示可用 `GATEWAY_BASE_URL` 指向别处 |
| 连上了但非 200 | 栈起了但网关不健康 → 引导 `docker compose logs gateway` |

两条都要把**实际探测的 URL 打出来** —— 它来自环境变量,可能并不指向你以为的地方。
异常本身也要带上(`type(exc).__name__` + `exc`),否则丢失了根因。

**面试点**:"你怎么看待测试框架的报错体验?" ——
测试失败信息的读者是**未来的自己和同事**,他们没有你此刻的上下文。
把"环境没起"和"代码写错了"区分清楚,能省下大量排查时间。
`pytest.exit` 还要传 `returncode=1`,CI 才能正确识别为失败。

## 3. HTTP 客户端收口:`**kwargs` 与"谁的 header 优先"　【实战 + 面试】

**改前**:`get / post / put / delete` 四个方法结构完全重复 —— 各自拼 URL、各自传
`headers=self._headers()`、各自写 `timeout=HTTP_TIMEOUT`。想加一条请求日志要改四遍。

**改后**:收口成一个 `request(method, path, **kwargs)`,四个方法各缩成一行转发。

```python
def request(self, method, path, **kwargs):
    url = self.base_url + path
    kwargs.setdefault("timeout", HTTP_TIMEOUT)
    caller_headers = kwargs.pop("headers", {})
    kwargs["headers"] = {**self._headers(), **caller_headers}
    return requests.request(method, url, **kwargs)

def get(self, path, **kwargs):
    return self.request("GET", path, **kwargs)
```

**收益不是少几行代码,是横切功能只改一处** —— 日志、重试、统一错误处理,以后都只写一遍。

### 3.1 `**kwargs` 的两个方向:打包与拆开

同一个 `**`,在**定义处**和**调用处**含义相反:

```python
def f(a, **kwargs):        # 定义处:把剩余的关键字参数【打包】成字典
    ...

f(1, x=2, y=3)             # kwargs == {"x": 2, "y": 3}

d = {"x": 2, "y": 3}
f(1, **d)                  # 调用处:把字典【拆开】成关键字参数
f(1, d)                    # 不加 ** —— 整个字典被当成位置参数塞给了 a,不报错但传错了
```

**最后一行是坑**:漏掉 `**` 不会报错,只是悄悄传到错误的位置上。转发时必须加。

### 3.2 默认值用 `setdefault`,别写死

```python
kwargs.setdefault("timeout", HTTP_TIMEOUT)   # 调用方传了就用它的,没传才填默认
```

如果直接写 `requests.request(..., timeout=HTTP_TIMEOUT, **kwargs)`,
调用方一旦也传 `timeout`,就会 `TypeError: got multiple values for keyword argument`。

### 3.3 header 合并:谁优先,取决于这是测试框架还是 SDK ⭐

> **SDK**(Software Development Kit,软件开发工具包):某个服务官方提供的、
> 给开发者调用的代码库。比如调 AWS 不用自己拼 HTTP,直接 `import boto3`;
> 底下还是 HTTP,但 SDK 帮你封装了鉴权、签名、重试、错误处理。
>
> `GatewayClient` 和 SDK 是同类东西 —— 都是"把 HTTP 细节包起来"。
> 但**用途正好相反**:
>
> | | 生产 SDK | 测试客户端 |
> |---|---|---|
> | 目的 | 让调用方**不会**犯错 | 让调用方**能故意**犯错 |
> | 鉴权头 | 锁死,防误改 | 要能改,否则测不了非法鉴权 |


`headers=self._headers()` 写成具名参数 + `**kwargs` 时,调用方传 `headers=` 会撞车。
解法是**先从 kwargs 里取出来再合并**,合并后塞回 kwargs,不再有具名的 `headers=`:

```python
caller_headers = kwargs.pop("headers", {})            # 取出并从 kwargs 移除,避免冲突
kwargs["headers"] = {**self._headers(), **caller_headers}
```

`{**a, **b}` 是字典合并,**后面的赢**。所以顺序决定优先级:

| 写法 | 谁赢 | 适合 |
|---|---|---|
| `{**框架, **调用方}` | 调用方 | **测试框架**(本项目选这个) |
| `{**调用方, **框架}` | 框架 | 生产 SDK |

**记忆点:后面的赢。** 想让谁赢就把谁放后面 —— 这是最容易记反的地方。
实测对照:

```
{**框架, **调用方}  → Authorization: 'Bearer FAKE'   ← 调用方的生效了
{**调用方, **框架}  → Authorization: 'Bearer real'   ← 框架的把它压回去了
```

**这里选调用方优先,理由很具体:测试框架必须能构造非法请求。**
如果框架强行锁死鉴权头,负向鉴权用例就没法写了 —— 而那恰恰是本项目的重点覆盖面。

改完之后可以直接这样写负向用例,不必再为每个 token 新建一个 client:

```python
auth_client.get("/interaction/ping", headers={"Authorization": "Bearer garbage"})   # → 401
```

实测三个场景:正常 200 / 覆盖成非法 token 401 / 额外加自定义头 200(鉴权头未被冲掉)。

**面试话术**:「同一个语法,取舍方向由使用场景决定。生产 SDK 锁死凭证是为了防误改;
测试框架反过来,必须允许覆盖,否则测不了非法输入。」

### 3.4 顺带:HTTP 头不能放非 ASCII

验证覆盖功能时我拿中文当假 token,直接炸了:

```
UnicodeEncodeError: 'latin-1' codec can't encode characters in position 7-8
```

HTTP header 的值必须是 **latin-1 可编码**的(RFC 7230)。构造非法输入时要注意 ——
**这是"测试数据本身不合法"导致的失败,不是被测系统的问题**,别误判成 bug。

## 4. 工具的警告是信号,不是噪音　【实战 + 面试】

跑测试时有 15 条 PyJWT 警告:

```
InsecureKeyLengthWarning: The HMAC key is 18 bytes long,
which is below the minimum recommended length of 32 bytes for SHA256.
See RFC 7518 Section 3.2.
```

**第一反应不该是"怎么让它闭嘴",而是"它说的对不对"。**

追下去:`compose-dev-secret` 正好 18 字节;查 RFC 7518 §3.2,HS256 的密钥确实应当
不短于哈希输出长度(32 字节);密钥越短,离线暴力破解成本越低。**警告是对的。**

于是它从"噪音"变成了**风险清单里的第 5 条发现**(见 [`README.md`](README.md))。

**为什么不直接改长**:该密钥被 `docker-compose.yml`、`e2e-py/framework/config.py`、
`tests/framework/config.py`、`e2e/internal/config/config.go` 四处引用,
改一处就得同步四处,收益(消掉 15 行输出)配不上破坏面。**记录 > 修改 > 压制。**

**为什么不用 `filterwarnings` 压掉**:压制会把真实的安全信号一起藏起来。
`pytest.ini` 里加一行 `ignore::...` 确实能让输出干净,代价是下次真有问题也看不见了。

**面试话术**:「测试跑出来的警告我会先判断真伪。这条 PyJWT 警告让我发现了一个
被测系统的真实弱点,我把它写进了风险评估而不是压掉。**测试的产出不只是红绿,
还包括这些顺带发现的问题。**」

## 5. 容错与检错要分层:一个会把故障"吞掉"并让测试变绿的陷阱 ⭐　【实战亮点 + 面试】

### 现象

`test_request_counter_increments` 的结构是"读一次记 before,打个请求,再读一次记 after,
断言 after > before"。最初把状态码断言写在了最后:

```python
resp = auth_client.get("/metrics")
before = counter_total(resp.text, "gateway_http_requests_total")
auth_client.get("/interaction/ping")
resp = auth_client.get("/metrics")
after = counter_total(resp.text, "gateway_http_requests_total")
assert resp.status_code == 200     # ← 只检查了第二次的 resp
assert after > before
```

**如果第一次 `/metrics` 挂了会怎样?** 实测:

```
counter_total("{\"error\":\"internal server error\"}")  →  0.0     # 没有匹配行,返回 0
counter_total(正常的 metrics 文本)                      →  118.0
断言:  after > before  →  118.0 > 0.0  →  True          # 测试通过了
```

**第一次请求明明是坏的,测试却绿了。**
更糟的是:坏掉让 `before` 变成 0,反而让 `after > before` **更容易成立** ——
故障不但没被发现,还帮着把测试推向通过。

**一个会吞掉故障、还顺带帮你变绿的测试,比直接报错的测试危险得多。**

### 根因:容错设计的另一面

`counter_total()` 找不到指标时返回 `0.0` 而不抛异常 —— 这是**刻意的**,
因为"指标还没出现"和"值为 0"语义上一致(见第 1 条)。

但同一个容错行为,面对"响应压根不是 metrics 文本"时也返回 `0.0`,
于是把一个真故障静默吞掉了。**这不是设计错了,是职责没分清。**

### 原则

| 层 | 职责 | 本例 |
|---|---|---|
| 解析函数 | **容错** —— 缺数据就给零值,不炸 | `counter_total` 找不到返回 `0.0` |
| 调用方 | **检错** —— 先确认输入本身合法 | 用例里 `assert_status(resp, 200)` |

配套的写法是**断言贴着来源写** —— 拿到一个响应就当场验它,别攒到最后:

```python
resp = auth_client.get("/metrics")
assert_status(resp, 200)                    # ← 立刻验
before = counter_total(resp.text, ...)
...
resp = auth_client.get("/metrics")
assert_status(resp, 200)                    # ← 立刻验
after = counter_total(resp.text, ...)
assert after > before
```

攒到最后写有两个害处:分不清是哪一个响应坏了;以及像上面那样**根本发现不了**。

### 面试话术

> **Q:你这个解析函数为什么找不到指标不抛异常?**
>
> 因为"缺失"和"为零"在语义上是一回事,抛异常会逼调用方到处写存在性判断。
> **但正因为它容错,调用方就必须先断言响应本身合法** —— 否则一个 500 响应
> 会被解析成 0,而 0 恰好让"增量大于零"这个断言更容易成立,故障就被静默吞掉了。
> 我在用例里给每一次请求都紧跟了一个状态码断言,就是为了补上这一层。
> **容错和检错要分开:解析层不炸,调用层把关。**

**这条的价值在于**:它不是"我知道要写断言",而是"我知道我自己的容错设计会带来什么风险,
并且配了对应的防护"。能讲清一个设计的**代价**,比讲清它的好处更能说明理解深度。

## 6. 统计性断言的样本量要算,不能拍脑袋 ⭐　【实战亮点 + 面试】

### 起点:一条几乎没有检出能力的断言

负载均衡用例原先是这么写的:

```python
seen = set()
for _ in range(10):
    seen.add(resp.headers.get("X-Served-By"))
assert seen == {"storage-a", "storage-b"}
```

`seen` 是**集合**,集合只记"有没有"、不记"有几个"。实测三种分布在它眼里完全一样:

| 分布 | `set(served) == {a, b}` |
|---|---|
| 5:5 健康轮询 | 通过 |
| **9:1 严重倾斜** | **通过** |
| **1:9 几乎不轮询** | **通过** |

**打 10 次里有 9 次落在同一个后端,这条断言也发现不了。** 它实际上只验证了
"两个后端都活着",跟"轮询是否正常"没什么关系。

### 改法:从"有没有"升级到"均不均匀"

用 `collections.Counter` 数出每个后端的命中次数,再校验相对偏差:

```python
counts = Counter(served)
missing = set(backends) - set(counts)
assert not missing, ...                       # ① 有后端一次没命中 → 轮询异常/坏节点被跳过

expected = len(served) / len(backends)        # ② 期望值 = 总数 / 后端数
for backend in backends:
    deviation = abs(counts[backend] - expected) / expected
    assert deviation <= tolerance, ...        # ③ 相对偏差超容差 → 分布倾斜
```

两个易错点(我都踩了):

- `expected` 是**除法**不是减法 —— `len(served) - len(backends)` 得到 8,不是 5。
- 偏差要算**相对**的。`tolerance` 是 0.25 这种比例,拿绝对差跟它比是量纲不对。
  必须 `abs(实际 - 期望) / 期望`。

### 样本量该怎么定 —— 以及一次被实测推翻的建模

改完之后剩一个问题:**打多少次才够?**

**第一版推理(后来被实测否定,但方法本身值得保留)**:
并行执行时别的 worker 也在打同一个 `/storage` 路由,共享的轮询指针会被它们推动,
如果这种推动是随机的,我方观测就退化成近似 50/50 的随机采样 —— 那是个二项分布问题。

按这个假设做蒙特卡洛模拟 2 万轮(容差 25%):

| 样本量 | 允许区间 | 误报率 |
|---|---|---|
| 10 | 3.8 ~ 6.2 | **34.1%** ← 三次跑红一次 |
| 20 | 7.5 ~ 12.5 | 26.9% |
| 40 | 15 ~ 25 | 7.9% |
| 60 | 22.5 ~ 37.5 | 5.3% |
| **100** | **37.5 ~ 62.5** | **1.2%** ← 选这个 |
| 144 | 54 ~ 90 | 0.2% |
| 200 | 75 ~ 125 | 0.0%(收益饱和) |

理论也对得上:

```
B(n, 0.5) 的标准差         = sqrt(n)/2
容差 25% 允许的绝对偏差    = n/8
要 3 sigma(99.7% 不误报):  n/8 >= 3*sqrt(n)/2   →   n >= 144
```

按这个模型,**取 100**:误报率 1.2% 已经够低,而 100 次请求在本地不到 1 秒。

### ⚠️ 但实测把这个模型推翻了

写完之后我去验证"指针被打乱"这个前提到底成不成立 —— 开 3 个后台线程持续打
同一个 `/storage` 路由制造干扰,再观察自己连续 10 次的分布:

```
无干扰:        5 次测量,全部是 {'storage-a': 5, 'storage-b': 5}
3 线程干扰下:  5 次测量,依然全部是 {'storage-a': 5, 'storage-b': 5}
```

**分布纹丝不动。** 原因:轮询是**原子计数器递增**,是确定性的 ——
别人的请求插进来只是移动了相位,我连续 10 次拿到的仍然是严格交替的 a、b、a、b。
只有当"别人在我两次请求之间插入的次数"本身是奇偶随机的,才会打乱交替;
实测中这个条件没有出现。

**并行 6 轮实跑也全部通过**,与实测一致,与模型预测的 34% 误报不符。

### 修正后的结论

- **二项分布那套推理是"最坏情况上界"**,不是本例的真实风险。
  它成立的前提是指针被随机化;而确定性轮询下这个前提不成立。
- **100 个样本仍然保留**,但理由改了:不再是"否则会误报",而是
  **防御性余量** —— 万一将来负载均衡策略改成加权/随机、或后端副本数变化,
  确定性就没了,那时二项分布模型才真正适用。样本量大不吃亏(100 次本地 < 1 秒)。
- **真正的教训是:模型要拿实测检验。** 我先建模算出"必须 100 个样本",
  然后去验证模型的关键假设,发现假设不成立 —— 于是修正了结论而不是修正数据。

蒙特卡洛的完整数据仍附在下面(它回答的是"如果指针真被随机化,需要多少样本"):

### 面试话术

> **Q:你的统计性断言样本量怎么定的?**
>
> 先建模再实测,而且实测把我的模型推翻了一半。
>
> 建模:并行时别的 worker 会推动共享的轮询指针,如果推动是随机的,

## 7. 被测系统的防护机制会挡住测试自己　【实战亮点 + 面试】

### 现象:我的负载均衡测试被限流拦了

第 6 条算出来轮询用例需要 **100 个样本**才能让统计断言可靠。改成打 100 次之后,
用例直接失败 —— 而且报错信息一眼就说清了原因(这正是第 4 条那个断言层的价值):

```
期望状态码 200,实际 429
  请求: GET http://127.0.0.1:8080/storage/ping
  响应: {"error":"429 Too Many Requests"}
```

**我自己的测试触发了被测系统的限流。**

### 实测:单个客户端的上限正好等于 burst

```
第 1 次测:连续成功 20 次后被限流
第 2 次测:连续成功 20 次后被限流
第 3 次测:连续成功 20 次后被限流
```

三次完全一致,而 `configs/config.docker.yaml` 里配的正是 `rps: 10 / burst: 20`。
令牌桶初始满桶 20 个令牌,打光即拒 —— **单个源 IP 无论如何也拿不到 100 个样本**。

### 解法:利用框架已有的随机源 IP 分摊

限流是**按源 IP** 的,而 `GatewayClient.__init__` 每次都会生成一个随机 `X-Forwarded-For`。
所以开 10 个 client、每个打 10 次,就是 **10 个独立的限流桶**:

```python
served = []
for _ in range(10):                                # 外层:换 client = 换源 IP
    client = GatewayClient(token=valid_token())
    for _ in range(10):                            # 内层:10 次,远低于 burst=20
        resp = client.get("/storage/ping")
        assert_status(resp, 200)
        served.append(served_by(resp))
assert_round_robin(served, ("storage-a", "storage-b"))   # 两层都跑完才断言一次
```

实测:100 个样本,分布 `{'storage-a': 50, 'storage-b': 50}`。

**为什么每个只打 10 次而不是 19 次**:留余量。并行执行时随机 IP 有极小概率与别的
worker 撞上、共用一个桶。10 次对 20 的上限,留了一倍安全边际。

**这不是 hack** —— README 风险清单第 2 条写着「`TrustedProxies` 未显式收窄 →
客户端可伪造 `X-Forwarded-For` 影响限流键(**测试正是利用这点做隔离**)」。
框架本来就是这么设计的:每个 client 独立源 IP,正是为了让用例之间的限流互不干扰。

### 踩到的坑:断言的缩进又错了一级

改完之后 `assert_round_robin` 被放在了**外层循环内**(缩进 8 而非 4),
于是它跑了 10 次,分别在样本量为 10、20、……100 时各断言一次。

**它通过了,但纯属侥幸**:串行执行时轮询是确定的,10 个样本正好 5:5。
可按第 6 条那张表,**样本量 10 在并行下的误报率是 34%** ——
辛苦算出来的 100 样本,被这一级缩进作废了。

**判断口诀:这句话该在什么时候执行一次?** "全部收集完之后"→ 就得在所有循环外面。
(这已经是同一类缩进错误的第三次了:`ExitStack` 写在探针 `with` 外、
`assert_round_robin` 写在内层循环里、又写在外层循环里。
**缩进不是排版,是"这段代码属于谁、跑几次"。**)

### 面试话术

> 限流把我自己的负载均衡测试拦住了。我需要 100 个样本才能让统计断言可靠,
> 但单 IP 的 burst 只有 20。解法是利用框架已有的随机源 IP 设计,
> 开 10 个 client 分摊 —— **每个 client 一个独立的限流桶**。
>
> 这暴露了一个更普遍的问题:**被测系统的防护机制会成为测试的障碍**。
> 要么绕开(像这样按 IP 分摊),要么给测试环境放宽配置。
> 我选前者,因为改配置会让限流测试本身失去意义 —— 而限流正是这个网关的核心能力之一。

**延伸**:同类问题还有验证码、风控、防重放、幂等校验。
成熟团队的做法是给测试环境开"后门"(白名单 IP、测试专用 token),
但**开后门本身就是风险**,得权衡。能讲出这层权衡,说明你想过测试与生产的边界。

## 8. 一个位运算把 IP 地址空间砍了一半:CI 红了一个月的真凶 ⭐　【实战亮点 + 面试】

> 这条发生在同仓库的 Go 端到端套件(`e2e/`)里,不是 e2e-py。但**排查思路完全通用**,
> 而且它是"CI 长期红着没人管"这个常见状况的一个漂亮解剖。

### 现象

仓库里 `E2E` 工作流长期失败,唯一失败项是 `TestRateLimit_PerIPIsolation` ——
"一个全新的源 IP 不应该受另一个 IP 限流的影响"。

用例逻辑本身没问题:先用 IP-A 把限流打爆,再用 IP-B 发一个请求,断言 200。
但实际拿到 429。

### 排查:先怀疑用例,而不是被测系统

直觉容易滑向"网关的按 IP 限流坏了"。但**先看测试自己有没有骗自己** ——
IP 是测试生成的,那就先验证"生成的 IP 真的不同吗"。

生成函数长这样:

```go
var ipCounter uint32

func uniqueIP() string {
	n := atomic.AddUint32(&ipCounter, 1)
	return fmt.Sprintf("10.20.%d.%d", (n>>8)&0xff, (n&0xff)|1)
}
```

把前 10 个值算出来:

```
n=1  → 10.20.0.1
n=2  → 10.20.0.3
n=3  → 10.20.0.3   ← 与 n=2 相同
n=4  → 10.20.0.5
n=5  → 10.20.0.5   ← 与 n=4 相同
```

**`|1` 把最低位强制置 1**,于是每一对相邻的偶/奇计数值塌缩成同一个地址。
前 256 次调用只产生 **129 个不同 IP** —— 地址空间被砍掉一半。

`|1` 的意图大概是避开 `.0` 这个网络地址,但代价是制造了系统性碰撞。

### 为什么恰好打中这条用例

```
TestRateLimit_BlocksAfterBurst  取到 n=1 → 10.20.0.1
PerIPIsolation 的 busy          取到 n=2 → 10.20.0.3   (打爆它)
PerIPIsolation 的 fresh         取到 n=3 → 10.20.0.3   ← 同一个!
```

**"全新的 IP"根本不新**,它就是刚被打爆的那个桶。429 是网关的正确行为 ——
**被测系统是对的,测试是错的。**

### 修法

按 /24 逐个走 `.1` 到 `.254`(跳过 `.0` 网络地址与 `.255` 广播地址),走完换下一个块:

```go
idx := atomic.AddUint32(&ipCounter, 1) - 1 // 0-based
host := idx%254 + 1                        // .1 .. .254
block := (idx / 254) % 256                 // 第三段
return fmt.Sprintf("10.20.%d.%d", block, host)
```

验证:前 **65024** 次调用产生 65024 个不同 IP,**零碰撞**;
重启网关连跑 3 轮,套件全绿(修复前稳定复现失败)。

### 面试价值

**① "测试失败先怀疑谁"是个态度问题。**
测试红了,第一反应是"被测系统有 bug"还是"我的用例有 bug"?
这条里网关完全正确,错的是测试自己的数据生成。**测试代码也是代码,也会有 bug,
而且它的 bug 更隐蔽 —— 因为没人测试测试。**

**② 症状离病根很远。**
症状是"限流隔离失效",病根是"一个位运算导致地址碰撞"。
中间隔着"生成的 IP 不唯一"这一层,不去验证这个中间假设就永远查不到。
**排查的本质是逐个验证隐含假设**,而不是盯着报错行反复看。

**③ 静默降级最难查。**
这个 bug 不会抛异常、不会报错,只是让地址空间悄悄少一半。
如果 `uniqueIP` 有一行单元测试断言"连续调用返回不同值",它活不过一天。
**给测试工具本身写测试,不是过度设计。**

**④ 长期红着的 CI 等于没有 CI。**
这条挂了很久没人修,久到大家习惯了"E2E 那个一直是红的"。
**一旦某个检查被默认忽略,它就失去了全部价值** —— 真出问题时也没人看。
