# 通用测试面试题(体系化答法)

面试问"XX 怎么测"最忌想到哪说到哪。**先立维度框架,再逐维展开**——既有条理又不漏。

---

## 一、万能模板:"XX 怎么测?"就套这 8 个维度

不管让你测登录框、购物车、还是一只杯子/一部电梯,都按这个顺序过一遍(顺着"用户怎么用 → 极端情况 → 非功能"):

1. **功能测试**:正向(正常流程走通)+ 反向/异常(错误输入、非法操作)+ 边界值。← 主体
2. **界面 / UI**:布局、样式、文案、控件状态、响应式(不同分辨率)。
3. **交互 / 易用性**:操作是否顺畅、提示是否清晰、快捷键、无障碍。
4. **兼容性**:浏览器/设备/OS/分辨率/网络环境。
5. **性能**:响应时间、并发、资源占用、长时间稳定性。
6. **安全**:鉴权、越权、注入(SQL/XSS)、敏感数据泄露、防刷。
7. **异常 / 可靠性**:弱网、断网、超时、中断、服务挂掉后的降级与恢复。
8. **数据**:准确性、一致性、边界(空/超长/特殊字符)、并发下的正确性。

> 讲的时候先报一句:"我会从功能、界面、兼容、性能、安全、异常这几个维度来测",再挑重点展开。**面试官要的就是这个体系感。**

### 示范:"一个登录框怎么测?"
- **功能**:正确账号密码登录成功;错误密码/不存在账号/空值 → 对应报错;记住密码、验证码、登录态保持。
- **界面**:输入框/按钮样式、密码掩码、错误提示位置。
- **兼容**:主流浏览器、手机端、不同分辨率。
- **性能**:登录接口响应时间、高并发登录。
- **安全**:密码是否加密传输、SQL 注入、暴力破解锁定、越权、验证码防刷。
- **异常**:断网时提交、重复点击、超长输入、后端超时。

## 二、★ 网页测试 vs 移动端测试的区别(按维度对比讲)

核心一句:**移动端多了"设备碎片化、网络多变、系统中断、传感器/手势、资源敏感"这几类,网页没有或很弱。**

| 维度 | 网页(Web) | 移动端(App) |
|---|---|---|
| **兼容性** | 浏览器 × 版本 × 分辨率 | 设备型号 × OS(iOS/Android)× 版本 × 屏幕尺寸 × 厂商 ROM,**碎片化严重得多** |
| **网络** | 一般 wifi/宽带 | 必须测**弱网、断网、网络切换(wifi↔4G/5G)、流量消耗** |
| **交互** | 鼠标 + 键盘 | **手势(滑动/多点触控)、横竖屏切换、传感器(GPS/摄像头/指纹)** |
| **中断** | 基本无 | **来电/短信/通知/切后台/被杀进程/低电量** 等系统中断(移动端特有) |
| **性能关注点** | 加载速度、并发 | 还要看**耗电、发热、内存、流量、启动速度、安装包大小** |
| **安装/升级** | 无(打开即用) | **安装/升级/卸载/权限申请** 要专门测 |
| **常用工具** | Selenium / Playwright | **Appium / UIAutomator2(安卓)/ XCUITest(iOS)** |
| **测试环境** | 浏览器 | **真机 + 模拟器**(真机更贴近,模拟器覆盖机型) |

> 答题套路:先说共同点(功能/UI/兼容/性能/安全都要测),**再重点讲移动端多出来的那几块**——碎片化、弱网、系统中断、传感器手势、资源敏感、安装升级。

## 三、CI/CD 相关

**Q:CI/CD 是什么?**
CI(持续集成)= 每次提交自动构建 + 跑测试,尽早发现问题;CD(持续交付/部署)= 自动把通过的版本发到测试/生产环境。核心是**自动化 + 快速反馈**。

**Q:什么样的项目适合/需要 CI/CD?★**
- 迭代快、多人协作 → 需要 CI 防止互相破坏、快速回归。
- 有一定自动化测试基础(单元/接口)→ CI 才有东西跑、才有门禁价值。
- 部署频繁 → CD 减少手工发布出错。
- 反过来:一次性脚本、几乎不改的项目,ROI 低,可以简单点。

**Q:CI/CD 的好处?**
尽早发现缺陷(左移)、每次提交都有质量门禁、回归自动化、发布可重复可回滚、团队协作更顺。

**Q:你项目里 CI 怎么做的?**(结合本项目)
GitHub Actions:push/PR → 起 docker compose 栈 → 两阶段跑 pytest(并行+熔断串行)→ k6 压测(性能门禁)→ 传 Allure 报告,任一失败拦 PR。

**Q:CI 里测试挂了怎么办?**
看报告定位是"真 bug"还是"用例/环境问题";真 bug 打回开发;flaky 找根因(共享状态/时序/环境)而不是简单 retry。

## 四、其它高频通用题

**Q:测试用例设计方法有哪些?**
等价类划分、边界值分析、因果图/判定表、场景法、错误推测法、正交实验(参数组合)。日常最常用:等价类 + 边界值 + 场景 + 异常/负向。

**Q:一个完整的测试流程?**
需求评审 → 测试计划/用例设计 → 环境准备 → 执行(冒烟→全量)→ 缺陷跟踪 → 回归 → 测试报告/上线评估。

**Q:测试金字塔?接口测试为什么重要?**
底层单元测试(多、快、稳)→ 中间接口/集成测试 → 顶层 UI 测试(少、慢、脆)。接口测试性价比最高:比 UI 稳定快速、又能覆盖业务逻辑,是自动化的主战场。

**Q:什么该做自动化?**
稳定的、重复执行的、回归频繁的、核心链路的用例适合自动化;需求频繁变动的 UI、一次性的探索测试不适合。

**Q:缺陷的等级和优先级区别?**
等级(严重程度)看对系统的影响(崩溃 > 功能错 > 界面小问题);优先级看修复的紧急度。二者不一定一致(如首页文案错:等级低但优先级可能高)。

**Q:冒烟 / 回归 / UAT?**
冒烟=最基本功能先跑通(不通就打回);回归=改动后重跑相关用例防引入新问题;UAT=用户/业务方验收。

**Q:黑盒 / 白盒 / 灰盒?**
黑盒只看输入输出(功能测试);白盒看内部代码逻辑(单元测试、覆盖率);灰盒介于两者(比如接口测试,知道部分内部结构)。

**Q:怎么保证测试质量 / 不漏测?**
需求覆盖(用例追溯到需求)、维度框架(上面那 8 维)、评审用例、覆盖率参考、缺陷复盘、探索式补充。
