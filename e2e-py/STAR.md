## STAR — 展开版(面试口述,围绕上面简历那几句展开)

**S — 情境**
一个承担鉴权、限流、反向代理、负载均衡、熔断的 Go API 网关,是所有微服务的统一入口。它每次改配置(加路由、调限流)都靠手工 curl 验证,没有自动化回归,异常路径(熔断、超时)更是几乎没法稳定验证。

**T — 任务**
从 0 搭一套接口自动化框架,覆盖网关核心能力,能稳定复现异常场景,并接入 CI 做每次提交的自动回归门禁。

**A — 行动**
1. **分层设计**:配置层(环境变量驱动,切环境零改代码)、客户端封装层(鉴权头/独立源 IP/超时)、JWT 工厂(正向 + 过期/错签名/算法混淆等负向)、断言,四层解耦,用例只写业务意图。
2. **可控测试桩做故障注入**:后端 mock 支持 `?status=`(强制任意状态码)、`?delay=`(注入延迟)、内存 CRUD,从而**稳定复现**熔断状态机(closed→open→half-open→closed)与上游超时(504)——这些异常路径用真实后端几乎无法确定性复现。
3. **数据驱动**:鉴权负向/安全用例外置到 YAML,加一行 = 加一个攻击面。
4. **契约测试**:用 JSON Schema 校验真实响应结构,面向契约而非面向实现。
5. **性能压测**:k6 以远超阈值的并发压限流,断言 429 触发 + p95 延迟 + 无 5xx,thresholds 接入 CI 做性能门禁。
6. **并行 + 隔离**:按"是否共享服务端状态"把用例分两组——大部队 `pytest-xdist` 并行,破坏性的熔断用例单独串行。
7. **CI 门禁**:GitHub Actions 每次 push/PR 自动起栈 → 两阶段跑 pytest → k6 压测 → 传 Allure 报告,任一失败拦 PR。

**R — 结果**
- **21 条用例 / 9 模块**全绿;回归从手工数十分钟 → 自动**约 16 秒**,并行提速约 3×。
- k6 压测:**14000 req/s** 下限流**精确**放行 ~122 个(≈ burst20 + rps10×10s),其余 141,625 全部 429,p95 2.4ms,零 5xx。
- 做成 PR 自动回归门禁;额外产出 **4 条有依据的设计风险评估**。

## 遇到的问题 / 难点 / 怎么解决(核心谈资)

> 这几条是最能体现工程能力的,面试时挑 2~3 个展开。

### 1. 测试隔离踩坑:一个逗号引发的跨用例串扰(★最推荐讲)
- **现象**:并行跑时,一个**路由测试**莫名返回 429,但它只发了一个请求。
- **排查**:先提假设"限流用例打空了共享的桶";没有瞎猜,而是做**最小实验**——手动用两个不同 IP,发现隔离本身是好的,排除"网关不认 XFF";再**打印 client 实际生成的 source_ip**,看到 `10.(<module 'random'...>, 206)...` 一坨垃圾。
- **根因**:随机 IP 的 f-string 里多写了个逗号 `{random, random.randint(...)}` → 变成元组 → 非法 IP → 网关解析不了 `X-Forwarded-For`,退回用真实连接 IP → 所有 client 挤回**同一个限流桶** → 限流用例一打空就连累别人。
- **收获**:症状离病根十万八千里;flaky 的头号成因是**共享状态**;调试三板斧——提假设→做实验证伪→打印真实值。

### 2. 破坏性用例污染:并行让熔断连累了超时
- **现象**:`pytest -n auto` 全并行时,超时用例期望 504 却拿到 503。
- **根因**:熔断用例和超时用例都打 `/compute`;熔断是**按路由的服务端共享状态**,并行时熔断被打开,超时请求被短路成 503。
- **解决**:按"是否共享服务端状态"分组——`pytest -m "not breaker" -n auto`(并行)+ `pytest -m breaker`(串行独占),既提速又不 flaky,并写进 CI。

### 3. "本地能跑,CI 挂":.gitignore 误伤源码
- **现象**:本地全绿,CI 一到构建后端就 `stat /app/cmd/mockbackend: directory not found`。
- **根因**:`.gitignore` 里写了裸名 `mockbackend`(本意忽略编译出的二进制),把 `cmd/mockbackend/` **源码目录**也忽略了 → 从没提交 → CI 全新拉取时缺失。
- **解决**:把二进制名**锚定到根目录** `/mockbackend`,再补提交源码。教训:gitignore 二进制名要加 `/`。

### 4. 限流功能测试难触发 → 分工:pytest 测功能,k6 测性能
- **现象**:顺序发 200 个请求都触发不了 429(发送速率刚好被令牌桶补充速率抵消)。
- **解决**:把测试环境限流阈值调低,让**功能测试**确定性触发 429;真正的高并发**性能测试**交给 k6(单机 14k req/s)。分清"功能测试"和"压测"的边界。

### 5. 发现网关缺陷并修复:上游无独立超时
- **现象**:后端再慢,网关也只会傻等,不会返回超时错误。
- **解决**:先用"特征测试"把这个短板固化,再给网关**加上上游超时**(context 超时 → 504),测试从"证明没有超时"**翻转**为"断言 504",体现"修复前后测试怎么变"。

### 6. 环境/网络:国内拉镜像与依赖
- Docker 拉镜像慢 → 配镜像加速器;容器内 `go mod download` 频繁 EOF → 改为**主机 vendor 依赖 + 容器离线构建**;`localhost` 请求慢 60s → 换 `127.0.0.1` 规避 Windows 的 IPv6 解析坑(60s → 0.09s)。


### 7. 指标断言的顺序依赖:一个"本地隐形、CI 常态"的 flaky(★推荐讲)

- **现象**:`test_metrics_exposed` 断言 `"gateway_http_requests_total" in resp.text`,
  本地怎么跑都绿,CI 上间歇性失败。
- **排查**:先确认不是网关坏了。手动重启网关后立刻 curl `/metrics`,发现**这个指标名一行都没有**;
  随便打一个业务请求再看,它就出现了。于是问题从"测试为什么挂"变成"指标为什么会消失"。
- **根因**:`internal/metrics/metrics.go` 里它是带 label 的 **`CounterVec`**(`{method,route,status}`),
  而 Prometheus 客户端对**零观测的 CounterVec 完全不输出** —— 连 `# HELP` / `# TYPE` 说明行都没有。
  刚启动、还没处理过任何业务请求的网关上,`/metrics` 里搜不到这个名字。**这是客户端库的正常语义,不是缺陷。**
- **为什么本地发现不了**:本地栈一开就是几小时,指标早被喂满;CI 每次 `docker compose up --build`
  都是全新网关。**这个 flaky 在开发机上几乎隐形,在 CI 上却是常态** —— 最难查的那一类。
- **为什么串行也不报**:串行执行时 `test_auth.py` 按文件名字母序排在 `test_ops.py` 前面,
  它打的请求顺手把指标喂了出来。换 `-n auto` 并行,这条用例可能抢在所有业务请求之前跑完。
  **它依赖的从来不是自己的操作,而是"别人恰好先跑过"。**
- **解决**:把断言从**存在性**改成**增量** —— 读一次 `/metrics` 记 `before`,
  打一个 `/interaction/ping`,再读一次记 `after`,断言 `after > before`。
  这样用例只依赖自己的操作,与执行顺序、网关新旧都无关。用例同步更名为
  `test_request_counter_increments`(名字该描述断言什么,而不是调了哪个接口)。
- **两个实现取舍**:
  - 配套的 `framework/prometheus.py` 里 `counter_total()` **找不到指标时返回 `0.0` 而非抛异常** ——
    "指标不存在"和"值为 0"语义上是一回事,这样调用方能直接写 `after > before`,不必先判断存在性。
  - 断言写 `after > before` 而**不是** `after == before + 1`。并行时别的 worker 也在打这个网关,
    计数器涨的不止 1。**共享环境里应当断言变化的方向,而不是精确值。**
- **验证**:重启网关(指标完全清空)后连跑 4 轮 `-n auto`,全部 19 passed;修复前同样条件稳定复现 `1 failed`。
- **收获**:三点。① **"测试挂了"不等于"被测系统坏了"** —— 先分清是实现缺陷还是自己对语义理解错了;
  ② **本地绿、CI 红的根源常是环境新鲜度差异**,不是玄学;
  ③ 一条用例如果依赖"别人先跑过",它就不是独立用例 —— **判断标准是:单独跑它,还成立吗?**

## 框架还能优化的地方(future work,面试主动说)

> 每条都按 **缺点 → 思路 → 怎么改 → 效果** 讲,体现"我知道现状不足 + 有可落地的改进路径"。

### 1. 客户端 DRY(消除重复)
- **缺点**:`get/post/put/delete` 各自重复拼 URL、组头、设超时,4 个方法几乎一样;想加个统一日志/重试要改 4 遍。
- **思路**:提取单一核心方法,其余委托它。
- **怎么改**:写 `_request(method, path, **kwargs)` 负责拼 URL/注入头/超时/发请求;`get/post...` 只 `return self._request("GET", path, **kw)`。
- **效果**:样板集中一处,加日志/重试/Allure 附件只改一个地方,代码量减半、更易维护。

### 2. 会话级探活夹具(fail fast)
- **缺点**:栈没起时每条用例各自去连、各自超时,报一屏红,看不出"其实是环境没起"。
- **思路**:开跑前统一探活一次,不通就立刻带指引退出。
- **怎么改**:conftest 加 `@pytest.fixture(scope="session", autouse=True)`,请求 `/healthz`,失败 `pytest.exit("先 docker compose up ...")`。
- **效果**:环境问题 3 秒内明确报出并给操作指引,不再被一堆连接超时误导,新人体验好。

### 3. 更严的质量闸(strict-markers + filterwarnings)
- **缺点**:打错 marker 名(loadbalance vs loadbalancing)时 `-m` 静默选不中、不报错(踩过一次);JWT 密钥长度警告刷屏。
- **思路**:让错误尽早显式失败,噪音过滤掉。
- **怎么改**:`pytest.ini` 的 `addopts` 加 `--strict-markers`;加 `filterwarnings` 忽略该警告(或换 ≥32 字节密钥)。
- **效果**:marker 拼错立即报错、不再静默漏跑;报告只剩有用信息。

### 4. 契约测试吃 OpenAPI(单一真相源)
- **缺点**:schema 内联在测试里,和 `docs/openapi.yaml` 是两份、可能不一致;契约变了测试不会自动跟。
- **思路**:直接从 openapi.yaml 取 schema 校验,契约文件成为唯一真相源。
- **怎么改**:用 `prance`/`openapi-spec-validator` 解析 openapi.yaml 提取响应 schema 喂给 jsonschema;或用 `schemathesis` 基于 OpenAPI 自动生成契约测试。
- **效果**:契约一改测试自动跟,不用维护两份;还能自动生成用例。

### 5. k6 参数化 + 更多场景
- **缺点**:base_url 硬编码 `127.0.0.1`;只有一个固定瞬时峰值场景。
- **思路**:环境可切、场景可扩。
- **怎么改**:脚本读 `__ENV.BASE_URL`;options 加 `stages`(阶梯加压 ramp-up)、加长时间 soak、加更多 thresholds。
- **效果**:一套脚本压不同环境;能看限流在逐步加压/长稳下的表现,不只是瞬时峰值。

### 6. Allure 报告发布到 Pages(可分享链接)
- **缺点**:Allure 报告只在本地/CI 产物里,别人看不到。
- **思路**:CI 生成 HTML 报告并发布到 GitHub Pages。
- **怎么改**:CI 里 `allure generate` + `peaceiris/actions-gh-pages` 发到 gh-pages 分支。
- **效果**:每次跑完有一个**在线报告链接**,简历/PR 里直接给,专业度高。

### 7. 全局限流(Redis)+ 分布式测试(架构级)
- **缺点**:限流/熔断每实例内存态,多副本下非全局,有效阈值翻倍。
- **思路**:把计数外置到 Redis 做全局限流。
- **怎么改**:限流中间件改用 Redis(`INCR`+过期做固定窗口,或 Lua 脚本实现原子令牌桶);compose 加 redis。
- **效果**:多副本下限流真正全局;并新增分布式测试点(多副本同时压→总放行量受全局阈值约束)+ Redis 故障降级测试。

## 发现的风险 / 已知限制(4 条)

1. 限流/熔断为**每实例内存态** → 多副本非全局,需 Redis。
2. `TrustedProxies` 未收窄 → `X-Forwarded-For` 可伪造影响限流键。
3. 负载均衡**无后端健康检查** → 坏节点仍被轮询。
4. `/metrics` 公开无鉴权;JWT 用 HS256 对称密钥,无 issuer/audience 校验与轮换。

## 面试高频追问预演

- **怎么保证不 flaky?** ①按 IP 隔离限流桶(每 client 独立源 IP);②共享服务端状态的熔断用例串行独占并前后复位;③故障场景用可控桩做到确定性,不依赖真实后端。
- **熔断怎么测的?** 连续 `?status=500` 打到阈值使其打开,断言后续请求被**网关短路**(503 且**无 `X-Served-By`**,证明没到后端);冷却后进半开,放行一个探测,成功→关闭。用"有无 `X-Served-By`"精确区分"网关短路"与"后端错误"。
- **契约测试和普通断言区别?** 普通断言把"响应长啥样"写死在用例里,实现和用例易一起漂;契约测试以 Schema 为真相源校验结构,接口一偏离立刻暴露,维护成本低。
- **为什么选它当被测系统?** 它把常见后端能力(鉴权/限流/LB/熔断/可观测)浓缩在一个边界清晰的服务里,且自带可控测试桩,既能覆盖足够多测试类型,又不至于庞大到无法完全掌控。
- **并行怎么做的?为什么两阶段?** `pytest-xdist -n auto` 多进程并行(约 3× 提速);但熔断是**按路由的服务端共享状态**,并行会串扰 → 把用例按"是否共享服务端状态"分成**可并行**(`-m "not breaker"` 并行)和**必串行**(`-m breaker` 独占)两阶段跑。这是"识别隐藏耦合、保证隔离"的关键设计。
- **fixture 怎么设计的?scope 怎么选?** 环境探活/client 放 `conftest.py` 全局共享;重资源(client)用较大 scope 复用,有状态的(存储复位)用 function scope 保证隔离。**scope 的本质是"复用换速度 vs 隔离换干净"的权衡**。
- **数据驱动怎么做的?** 鉴权负向用例外置到 `data/auth_cases.yaml`,用 `@pytest.mark.parametrize` 读进来 → **加一行 YAML = 加一个攻击面,不动代码**;用例逻辑和数据分离。
- **契约测试的 Schema 从哪来?** 用 JSON Schema 描述响应结构,面向契约而非实现;更进一步可让 Schema 吃 OpenAPI 做单一真相源(future work)。
- **怎么切换环境?** 全走环境变量(`GATEWAY_BASE_URL` 等),**切环境零改代码**,指向别的实例即可 → 天然适配本地/CI/不同环境。
- **CI 门禁具体流程?** GitHub Actions 每次 push/PR:起栈 → 两阶段跑 pytest → k6 压测(thresholds 当性能门禁)→ 传 Allure 报告;任一环节失败即拦 PR。性能取舍详见 `PERFORMANCE-QA.md`。

## 两项目组合打法(选对弹药讲)⭐

你手里有**两个互补的项目**,按面试官的方向选一个主讲,别混为一谈:

| | **项目一:本项目(Go 网关 + pytest 框架)** | **项目二:投保系统性能压测** |
|---|---|---|
| 定位 | **接口/框架自动化 + 架构 + 故障注入**(你的主线) | **纯性能压测 + JVM/DB 调优 + 全链路监控**(你的尖刺) |
| 技术栈 | Python/pytest、Go、Docker、k6、GitHub Actions | JMeter、Grafana+Prometheus、Java/MySQL 调优 |
| 亮点 | 分层框架、数据驱动、CI 门禁、熔断/超时**故障注入**、容量基准+pprof | 试算/核保/承保三接口、**阶梯加压找拐点**、4 个调优案例(日志阻塞/慢查询/内存泄漏/线程池)、TPS 800 |
| 问"讲个项目" | 岗位偏**框架/测开/架构/自动化** → 讲这个 | 岗位偏**性能/稳定性/调优** → 讲那个 |

**打法**:
- 问框架/自动化/CI/如何设计 → **项目一**(本框架,细节见本目录各 QA)。
- 问性能/压测/调优/JVM/慢 SQL → **项目二**(材料在个人笔记的"项目二"系列 + 用本网关做的实操复现)。
- 两个项目正好覆盖简历定位:**接口框架自动化(主线)+ 性能故障注入(尖刺)**。

> ⚠️ **真实性铁律**:讲哪个项目,数字和细节都得是**你真跑过/真经历**的。性能类追问会追到 `jstack/jmap/EXPLAIN` 的**具体输出**,没实操过一问就穿帮。本框架的性能门禁(k6)、故障注入(熔断/超时)你真做过 → 讲透;没亲手复现的 Java 调优细节,老实说"方法我清楚、是配合开发定位的"(诚实边界比硬吹更可信)。
