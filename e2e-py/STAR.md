## STAR — 展开版(面试口述,围绕上面简历那几句展开)

**S — 情境**
一个承担鉴权、限流、反向代理、负载均衡、熔断的 Go API 网关,是所有微服务的统一入口。它每次改配置(加路由、调限流)都靠手工 curl 验证,没有自动化回归,异常路径(熔断、超时)更是几乎没法稳定验证。

**T — 任务**
从 0 搭一套接口自动化框架,覆盖网关核心能力,能稳定复现异常场景,并接入 CI 做每次提交的自动回归门禁。

**A — 行动**
1. **分层设计**:配置层(环境变量驱动,切环境零改代码)、客户端封装层(鉴权头/独立源 IP/超时)、JWT 工厂(正向 + 过期/错签名/算法混淆等负向)、断言,四层解耦,用例只写业务意图。
2. **可控测试桩做故障注入**:后端 mock 支持 `?status=`(强制任意状态码)、`?delay=`(注入延迟)、内存 CRUD,从而**稳定复现**熔断状态机(closed→open→half-open→closed)与上游超时(504)——这些异常路径用真实后端几乎无法确定性复现。
3. **数据驱动**:鉴权负向/安全用例外置到 YAML,加一行 = 加一个攻击面。
4. **契约测试**:用 JSON Schema 校验真实响应结构,面向契约而非面向实现。
5. **性能压测**:k6 以远超阈值的并发压限流,断言 429 触发 + p95 延迟 + 无 5xx,thresholds 接入 CI 做性能门禁。
6. **并行 + 隔离**:按"是否共享服务端状态"把用例分两组——大部队 `pytest-xdist` 并行,破坏性的熔断用例单独串行。
7. **CI 门禁**:GitHub Actions 每次 push/PR 自动起栈 → 两阶段跑 pytest → k6 压测 → 传 Allure 报告,任一失败拦 PR。

**R — 结果**
- **21 条用例 / 9 模块**全绿;回归从手工数十分钟 → 自动**约 16 秒**,并行提速约 3×。
- k6 压测:**14000 req/s** 下限流**精确**放行 ~122 个(≈ burst20 + rps10×10s),其余 141,625 全部 429,p95 2.4ms,零 5xx。
- 做成 PR 自动回归门禁;额外产出 **4 条有依据的设计风险评估**。

## 遇到的问题 / 难点 / 怎么解决(核心谈资)

> 这几条是最能体现工程能力的,面试时挑 2~3 个展开。

### 1. 测试隔离踩坑:一个逗号引发的跨用例串扰(★最推荐讲)
- **现象**:并行跑时,一个**路由测试**莫名返回 429,但它只发了一个请求。
- **排查**:先提假设"限流用例打空了共享的桶";没有瞎猜,而是做**最小实验**——手动用两个不同 IP,发现隔离本身是好的,排除"网关不认 XFF";再**打印 client 实际生成的 source_ip**,看到 `10.(<module 'random'...>, 206)...` 一坨垃圾。
- **根因**:随机 IP 的 f-string 里多写了个逗号 `{random, random.randint(...)}` → 变成元组 → 非法 IP → 网关解析不了 `X-Forwarded-For`,退回用真实连接 IP → 所有 client 挤回**同一个限流桶** → 限流用例一打空就连累别人。
- **收获**:症状离病根十万八千里;flaky 的头号成因是**共享状态**;调试三板斧——提假设→做实验证伪→打印真实值。

### 2. 破坏性用例污染:并行让熔断连累了超时
- **现象**:`pytest -n auto` 全并行时,超时用例期望 504 却拿到 503。
- **根因**:熔断用例和超时用例都打 `/compute`;熔断是**按路由的服务端共享状态**,并行时熔断被打开,超时请求被短路成 503。
- **解决**:按"是否共享服务端状态"分组——`pytest -m "not breaker" -n auto`(并行)+ `pytest -m breaker`(串行独占),既提速又不 flaky,并写进 CI。

### 3. "本地能跑,CI 挂":.gitignore 误伤源码
- **现象**:本地全绿,CI 一到构建后端就 `stat /app/cmd/mockbackend: directory not found`。
- **根因**:`.gitignore` 里写了裸名 `mockbackend`(本意忽略编译出的二进制),把 `cmd/mockbackend/` **源码目录**也忽略了 → 从没提交 → CI 全新拉取时缺失。
- **解决**:把二进制名**锚定到根目录** `/mockbackend`,再补提交源码。教训:gitignore 二进制名要加 `/`。

### 4. 限流功能测试难触发 → 分工:pytest 测功能,k6 测性能
- **现象**:顺序发 200 个请求都触发不了 429(发送速率刚好被令牌桶补充速率抵消)。
- **解决**:把测试环境限流阈值调低,让**功能测试**确定性触发 429;真正的高并发**性能测试**交给 k6(单机 14k req/s)。分清"功能测试"和"压测"的边界。

### 5. 发现网关缺陷并修复:上游无独立超时
- **现象**:后端再慢,网关也只会傻等,不会返回超时错误。
- **解决**:先用"特征测试"把这个短板固化,再给网关**加上上游超时**(context 超时 → 504),测试从"证明没有超时"**翻转**为"断言 504",体现"修复前后测试怎么变"。

### 6. 环境/网络:国内拉镜像与依赖
- Docker 拉镜像慢 → 配镜像加速器;容器内 `go mod download` 频繁 EOF → 改为**主机 vendor 依赖 + 容器离线构建**;`localhost` 请求慢 60s → 换 `127.0.0.1` 规避 Windows 的 IPv6 解析坑(60s → 0.09s)。

## 框架还能优化的地方(future work,面试可主动说)

1. **客户端 DRY**:`get/post/put/delete` 各自重复拼 URL/头/超时,可抽一个 `_request(method, path, **kwargs)` 核心方法,其余委托它。
2. **会话级探活夹具**:session 级先探一次网关是否就绪,栈没起时**快速失败并给清晰指引**,而不是每条用例各自超时报一堆红。
3. **更严的质量闸**:`pytest.ini` 加 `--strict-markers`(打错标记直接报错,避免之前 loadbalance/loadbalancing 那种坑)+ `filterwarnings` 消掉 JWT 密钥长度警告,报告更干净。
4. **契约测试吃 OpenAPI**:目前用内联 JSON Schema,可改为直接从 `docs/openapi.yaml` 提取 schema 校验,真正"以契约为唯一真相源"。
5. **k6 参数化**:压测脚本的 base_url 走 `__ENV`,便于压测不同环境;再加 ramp-up/soak 场景。
6. **Allure 发布**:CI 里把 Allure 报告发布到 GitHub Pages,拿到一个在线报告链接。
7. **全局限流(架构级)**:引入 Redis 做全局限流/熔断,并补对应的**分布式测试**(多副本下总量受全局限流约束)。

## 发现的风险 / 已知限制(4 条)

1. 限流/熔断为**每实例内存态** → 多副本非全局,需 Redis。
2. `TrustedProxies` 未收窄 → `X-Forwarded-For` 可伪造影响限流键。
3. 负载均衡**无后端健康检查** → 坏节点仍被轮询。
4. `/metrics` 公开无鉴权;JWT 用 HS256 对称密钥,无 issuer/audience 校验与轮换。

## 面试高频追问预演

- **怎么保证不 flaky?** ①按 IP 隔离限流桶(每 client 独立源 IP);②共享服务端状态的熔断用例串行独占并前后复位;③故障场景用可控桩做到确定性,不依赖真实后端。
- **熔断怎么测的?** 连续 `?status=500` 打到阈值使其打开,断言后续请求被**网关短路**(503 且**无 `X-Served-By`**,证明没到后端);冷却后进半开,放行一个探测,成功→关闭。用"有无 `X-Served-By`"精确区分"网关短路"与"后端错误"。
- **契约测试和普通断言区别?** 普通断言把"响应长啥样"写死在用例里,实现和用例易一起漂;契约测试以 Schema 为真相源校验结构,接口一偏离立刻暴露,维护成本低。
- **为什么选它当被测系统?** 它把常见后端能力(鉴权/限流/LB/熔断/可观测)浓缩在一个边界清晰的服务里,且自带可控测试桩,既能覆盖足够多测试类型,又不至于庞大到无法完全掌控。
